##  26. High-Value Feature Ideas to Try Later
#       Log transforms (log1p(x))
#         Great for strictly positive, heavy-tailed variables (volume, volatility, dollar values).
#       Ratios (x / y)
#         Useful when features naturally relate as “speed,” “intensity,” or “relative change.”
#       Differences (x - y)
#         Captures spread signals (fast vs. slow averages, value vs. threshold, etc.).
#       Standardized z-scores ((x - mean)/std)
#         Can help when a raw feature’s scale changes over time or has rolling structure.
#       Min–max scaling to range (0,1)
#         Sometimes helpful for users sensitive to absolute scale (occasionally improves
#         FLAML/GBMs).
#       Logistic squashing (1/(1+exp(-x)))
#         Helps tame extreme outliers and emphasize mid-range signals.
#       Clipped features (clip(x, lower, upper))
#         Reduces noise from extreme values while keeping the bulk signal intact.

##  98. Additional documentation for Feature Sensitivity:
        ####
        What it means if Feature Importance is high but Prediction Influence is low.
        It implies:
        The model relies on this feature a lot internally, but changing its typical values does not move predictions very much.
        The feature is used often or early in the model’s logic
        But within the range where data usually falls, the model’s output is fairly stable
        Common reasons this happens:
        The feature helps separate cases, but only in narrow or boundary situations
        The feature is highly correlated with others (shared information)
        The feature is important for structuring the model, not for driving big swings
        ####
        What it means if Feature Importance is low but Prediction Influence is high.
        It implies:
        The model does not rely on this feature very often internally, but when it changes, predictions can shift noticeably.
        The feature is used infrequently in the model’s logic
        But when it matters, it has a strong effect on the prediction
        Common reasons this happens:
        The feature is important only for a specific subset of cases
        The feature captures a sharp signal that applies in limited situations
        The feature affects predictions strongly, but only when certain conditions are met
        ####
        What it means if Feature Importance is low and Prediction Influence is low.
        It implies:
        The model rarely relies on this feature, and changing its typical values does not meaningfully affect predictions.
        The feature plays a minor role in the model’s logic
        And its values do not cause noticeable changes in predictions
        Common reasons this happens:
        The feature adds little useful information
        The feature may be noisy or redundant
        The feature does not help distinguish between different cases
        ####
        What it means if Feature Importance is high and Prediction Influence is high.
        It implies:
        The model relies heavily on this feature, and changes in its typical values strongly affect predictions.
        The feature is used frequently or early in the model’s logic
        And variations in the feature lead to substantial changes in predictions
        Common reasons this happens:
        The feature captures a core signal in the data
        The feature directly influences the model’s decisions
        The feature explains a large share of the model’s predictive behavior

Title
Why Your Machine Learning Metrics Are Lying to You
Article
Writing
When you first start building machine learning models, metrics feel like the ultimate source of truth.
Accuracy, RMSE, R² — they give you a number. And that number feels objective.

But in practice, metrics can be surprisingly misleading.

After working on a number of tabular ML problems (both in Kaggle and real-world settings), I kept running into the same pattern:

Models that looked good on paper didn’t actually perform as well as expected.

Here are a few common failure modes.

1. Beating a baseline doesn’t mean much
It’s easy to celebrate when a model outperforms a naive baseline.
But the real question is: by how much?

If your model improves accuracy from 50% to 52%, that may not be meaningful. It could be noise, especially depending on your validation setup.

Without a strong baseline comparison, it’s hard to know whether you’ve actually built something useful.

2. Small improvements are often noise
Many ML workflows optimize for incremental gains.
But small metric improvements can be fragile:

they may disappear with a different random seed
they may depend on a particular train/validation split
they may not generalize to new data
If an improvement isn’t consistent, it’s probably not real.
3. A single validation score hides instability
Most people look at the average cross-validation score.
But averages can hide a lot.

Two models with the same mean score can behave very differently:

one is stable across folds
the other varies significantly
In practice, the stable model is usually more reliable.
Looking at variance (or worst-case performance) often reveals issues that the mean hides.

4. Train vs validation gaps matter more than you think
A model that performs extremely well on training data but drops on validation data is often overfitting.
This isn’t always obvious if you only focus on the validation score.

The relationship between train and validation performance is often more informative than either number alone.

5. Metrics don’t tell you if the model is useful
A model can have a “good” metric and still not be useful in practice.
For example:

it may not outperform simple heuristics by much
it may not be stable enough to trust
it may rely on patterns that don’t generalize
Metrics measure performance, but not necessarily usefulness.
A more reliable way to evaluate models
Over time, I’ve found a few checks to be consistently helpful:
Compare against simple baselines
Look at train vs validation behavior
Check stability across folds
Be skeptical of small improvements
These are simple ideas, but they prevent a lot of wasted effort.
Why I built a tool for this
After running into these issues repeatedly, I built a small tool to make these signals more visible when working with tabular data.
The goal isn’t to replace existing ML libraries, but to add a layer of sanity checks:

baseline comparisons
overfitting signals
validation stability
If you’re interested, you can try it here: https://predictly.cloud
Final thought
It’s easy to optimize for better numbers.
It’s much harder — and more important — to make sure those numbers actually mean something.

And in many cases, the difference between the two is what separates a model that looks good from one that actually works.
